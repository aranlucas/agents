# Software Engineering Interview Coach

## Overview

Add a private `interview` agent to the existing Go ADK gateway and web console. The agent conducts realistic software-engineering interview practice in two tracks:

- Behavioral: asks one question at a time, probes vague answers, coaches the user toward a concise STAR response, and records reusable story notes.
- Coding: selects a curated LeetCode-style problem by topic and difficulty, asks the user to reason before coding, gives progressive hints only when requested or when the user is stuck, and reviews correctness, complexity, edge cases, and communication.

The first version is a single stateful agent with deterministic tools and a custom practice-board artifact. It does not execute arbitrary user code and does not require retrieval, external APIs, or new deployment infrastructure.

## Architecture

### Chosen approach: standalone single agent

Create a separate `interview` package, catalog entry, gateway binding, shared generated state contract, and web artifact. The agent owns a typed interview-session state and uses local tools to configure a session, select or record a question, evaluate an answer, and complete a session summary.

This keeps interview practice distinct from the in-progress `jobs` agent, whose responsibility is job research, matching, resume tailoring, and application drafting.

### Alternatives considered

1. Extend the `jobs` agent. This would reduce the number of catalog entries, but would mix application workflow state with a repeated practice loop and make the UI artifact unfocused.
2. Use a coordinator with behavioral and coding sub-agents. This creates cleaner specialist prompts but adds routing and state-handoff complexity before the core coaching loop has been validated.
3. Use a standalone single agent. This is the recommended first slice because both tracks share the same session lifecycle, scoring model, and coaching rules while remaining easy to split later.

## Example Use Cases

### Behavioral mock interview

Input: "Give me a senior engineer behavioral interview focused on conflict and influence."

Expected flow:

1. Configure a behavioral session for a senior-engineer level.
2. Ask one interview question without showing an ideal answer.
3. Ask targeted follow-ups when the answer lacks context, personal actions, measurable results, or reflection.
4. Give evidence-based feedback and a stronger answer outline after the attempt.
5. Continue until the requested question count is complete, then summarize strengths and focus areas.

### Coding practice

Input: "Practice a medium graph problem with me. Interview mode, so do not give away the solution."

Expected flow:

1. Select a medium graph problem from the local bank.
2. Present the prompt, examples, and constraints.
3. Ask for clarification, a naive approach, and complexity before code.
4. Give progressive hints only when asked or after a clearly blocked attempt.
5. Review the submitted reasoning or code for correctness, complexity, edge cases, and interview communication.
6. Record a concise score and next practice recommendation.

### Targeted answer review

Input: "Here is my answer to 'tell me about a conflict with a PM.' Help me make it interview-ready."

Expected flow:

1. Treat the supplied answer as the current attempt.
2. Identify missing STAR elements without inventing experience.
3. Ask for missing factual details before proposing a rewrite.
4. Produce a concise improved outline or answer using only user-provided facts.

## Tools Required

All tools are local Go function tools and require no external authentication.

- `configure_interview`: stores track, target role/level, focus topics, question count, and coaching style; resets stale session progress.
- `select_question`: deterministically selects an unused behavioral or coding question matching the configured filters.
- `record_attempt_feedback`: records the user's attempt summary, rubric scores, strengths, improvements, and follow-up prompt.
- `request_hint`: advances through bounded coding hints without revealing the complete solution too early.
- `complete_interview`: validates that the configured practice loop is complete and writes a session summary plus next steps.

The existing authenticated web session is the only access control. The existing provider-policy model chain remains unchanged; the agent does not hardcode a new model.

## State and Data Flow

Session state includes:

- track, target role, target level, topics, coaching style, and target question count
- current question and question history
- current attempt count and hint level
- per-question rubric scores, strengths, improvements, and follow-up
- completed-question count, aggregate score, session status, summary, and next steps
- behavioral story notes containing only facts explicitly provided by the user

The local question bank contains original prompts and metadata, not scraped or copied proprietary LeetCode content. Coding entries include constraints, examples, progressive hints, expected complexity, and a private evaluator rubric. Behavioral entries include competencies and follow-up probes.

## Constraints and Safety Rules

- Ask one interview question at a time.
- Do not reveal a complete coding solution before the user makes a meaningful attempt unless the user explicitly exits interview mode.
- Never claim code passed tests because the first version does not execute arbitrary code.
- Distinguish code inspection from runtime verification.
- Do not invent behavioral achievements, metrics, employers, or project details.
- Ask for missing facts before rewriting a behavioral answer.
- Score only against explicit rubric dimensions and cite concrete evidence from the user's attempt.
- Avoid protected-trait inference and do not coach deceptive answers.
- Keep current `jobs` changes intact and do not merge its application state into interview state.
- Preserve the existing D1/R2 persistence architecture and gateway deployment.

## Success Criteria

- Backend unit tests cover defaults, question filtering, no-repeat selection, progressive-hint bounds, rubric validation, and completion guards.
- Contract/catalog tests prove the `interview` client ID, route, app name, state schema, and gateway binding agree.
- Web tests cover empty, active-question, feedback, and completed-session practice-board states.
- At least six agent eval cases cover: behavioral mock, factual answer rewrite, coding no-spoiler flow, requested hint, code-review honesty, and session completion.
- In the no-spoiler eval, the agent does not provide a full solution before a meaningful attempt or explicit opt-out.
- In the behavioral-grounding eval, the agent introduces no unsupported personal facts.
- `pnpm check` and `pnpm test` pass without modifying or deleting unrelated in-progress work.

## Assumptions

- Assumed this should be a separate authenticated agent rather than part of the `jobs` agent.
- Assumed the first version should support both behavioral and coding practice equally.
- Assumed a local curated question bank is preferable to a third-party question API.
- Assumed no external authentication, schedule, long-term cross-session memory, or code-execution sandbox is needed for the first version.
- Assumed the existing provider-policy model selection should be preserved instead of selecting a new model.
- Assumed prototype-first delivery in the current gateway and web console, with no production deployment in this task.

## Future Phases

- Sandboxed multi-language code execution against hidden tests.
- Cross-session skill history and spaced-repetition scheduling.
- Company-specific interview loops grounded in current public sources.
- Separate behavioral and coding specialist agents if evals show the unified prompt is unreliable.
